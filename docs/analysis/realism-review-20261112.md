# ABank 功能、页面与资源完善评估

评估日期：2026-11-12；代码基线 `main@e03f8d7`。方法：iOS 原生设计复核、源码核对、隔离运行截图。网页检测器不适用；本轮没有改业务代码、导入新素材或进行提交。

## 结论

现有“我的”、账户、收支明细和贷款首页已经形成比较稳定的视觉方向，账本核心也具备共享数据、重复提交防护及保存失败保护。下一阶段应先补齐入口含义、账户上下文和日期状态，再精修账单分析、回单及业务二级页，最后补充存款、信用卡等高频业务。

继续沿用已确认的银行页面风格：白底、浅灰分区、紧凑信息行、绿色业务入口和既定金额色。保留已有37笔历史交易，不为填满页面随机增加工资、消费或还款。

## 实际检查范围与证据

- 核对243个功能区Swift文件中的关键入口、目录、账户及资金模型，重点追踪首页、财富、我的、账单、账户、贷款和二级业务页。
- 功能目录71项：35项标记可用、36项仍在规划。这里的“可用”来自目录声明，不等于所有入口、异常与设备场景都已完成验收。

## 数据真实感的具体方向

1. **每个值有唯一来源**：客户、账户、消息角标、持仓产品和账单摘要不再各有一套固定值。财务数量由记录派生，展示编号不暴露实现阶段（当前缴费订单号含M8前缀）或内部UUID。
2. **保存历史，显式处理时间**：历史37笔保留，日期选2027年时允许空月，并给历史查询入口；本金、已还、计划分别建模，不能为了显示“当前”而自动创造交易。
3. **增加状态而不填充假成功**：待确认、已提交、处理中、失败、已完成、已取消等仅在对应业务有明确本地规则时引入。状态变化与余额/冻结资金一次保存，重启与重复进入不重复扣款。
4. **给退款/冲正留关系**：新增记录关联原交易，保留原始金额、时间和原订单；不删除旧流水来伪装撤销。
5. **建立可复现的独立场景**：正常、空月、余额不足、多账户、挂失、还款计划到期、存量数据升级等用独立验证数据覆盖。场景数据不覆盖用户正常账本，也不需要把“测试/模拟”词放进产品页面。
6. **未知字段保留未知**：原始合同号、未提供完整卡号、原始交易时刻继续用占位，不从外观像真实转为编造事实。

## 实施顺序与每轮验收

- **第一轮：高频入口与数据一致性**。处理R01–R05，优先多账户付款、跨月应还、会话/持仓、消息中心及可办理入口。验收入口语义、状态持久化、跨月和资金守恒。
- **第二轮：账单与回单视觉精修**。处理R06–R08、R11、R13，先选账单分析、回单、产品详情三页建立统一二级页面规范；对照同版本参考图，正常/空/失败/长内容状态都留图。
- **第三轮：账户与交互细节**。处理R09–R10、R12、R14–R15，补账户能力、记账用途、隐私刷新规则、大字号和认证交互。
- **第四轮：高频业务扩展**。从存款、信用卡中先做一个独立闭环，再推进R16–R19；暂不全面铺开所有36个规划项。

建议默认从第一轮开始，随后精修账单分析与回单。所有数据修改继续使用本地规则，保留原有账本和未知字段，不接真实银行接口。
